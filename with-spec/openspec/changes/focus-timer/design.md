# Design

## Context

См. мотивацию в `proposal.md`. Проверенный состав проекта: `brief.md`, конфигурация OpenSpec и служебные инструкции; исходники, тесты и сборка отсутствуют. Существующих основных спецификаций нет. Решение создаётся с нуля на HTML, CSS и JavaScript без сторонних библиотек. `brief.md` требует отдельный `domain.mjs` и тестирование через `node:test`.

Дизайн нужен из-за взаимодействия часов, состояния сессии, задач и долговременного хранения. Контракты находятся в четырёх delta specs этого изменения.

## Goals / Non-Goals

**Goals:**
- Отделить проверяемые расчёты и переходы состояния от DOM, часов и localStorage.
- Завершать сессию согласованно: вычислить результат, скопировать задачи, обновить историю и сбросить текущую сессию.
- Сохранить локальный запуск без сборки и сетевых зависимостей.

**Non-Goals:**
- Не вводить фреймворк, менеджер состояния, серверное хранилище или сборщик.
- Не сохранять текущее состояние секундомера между перезагрузками и не синхронизировать несколько вкладок.
- Не обеспечивать защиту от ручного изменения системных часов; это не система учёта оплачиваемого времени.

## Decisions

### 1. Структура статического приложения

Планируемые файлы: `index.html`, `styles.css`, `app.mjs`, `domain.mjs`, `storage.mjs`, `tests/domain.test.mjs`, `tests/storage.test.mjs` и `README.md`. `app.mjs` связывает события и DOM, `domain.mjs` содержит чистые вычисления и переходы состояния, `storage.mjs` инкапсулирует формат истории и обработку ошибок. Модули импортируются браузером напрямую. Альтернатива — один большой скрипт — затрудняет изолированное тестирование; фреймворк противоречит ограничениям.

Для ES-модулей использовать локальную статическую раздачу по HTTP на localhost, без прикладной серверной части и доступа к интернету. В README дать конкретную команду доступного локального инструмента и указать требование Node.js для `node --test`. Прямое открытие `file://` не считать поддерживаемым способом запуска из-за ограничений модулей браузера.

### 2. Явное состояние сессии и передаваемые часы

Состояния: `idle`, `running`, `paused`. Хранить выбранную цель в миллисекундах, накопленное активное время, начало текущего активного отрезка и время первого старта. В `idle` разрешены выбор цели и старт; в `running` — пауза и завершение; в `paused` — продолжение и завершение. Недопустимые повторные действия не меняют состояние, что исключает повторное сохранение.

Все расчёты получают `nowMs` аргументом; браузер передаёт `Date.now()`. Активная длительность равна накопленному времени плюс разница текущего момента и начала активного отрезка. На паузе отрезок складывается в накопленное время; продолжение начинает новый отрезок. Интервал обновления лишь перерисовывает интерфейс; после задержки или возвращения вкладки время пересчитывается по меткам. Отрицательную разницу ограничить нулём.

Выбор абсолютных меток вместо подсчёта тиков предотвращает накопление задержек и учитывает время при приостановке обновлений браузера. Альтернатива `performance.now()` устойчива к переводу часов, но поведение при сне системы различается по платформам. Ограничение текущего выбора — скачки системных часов; восстановление после них вне объёма.

Расчёты и сравнение с целью выполнять в миллисекундах, отображаемые секунды округлять вниз. Формат часов не оборачивать после 24 часов. Прогресс ограничивать диапазоном 0–100. При завершении на паузе учитывать только накопленное время; сравнение с целью производится до округления. После завершения выбранная цель остаётся прежней; после загрузки выбирается 60 минут.

### 3. Единая операция завершения и задачи

Задачи имеют стабильный идентификатор, обрезанное по краям название и булев статус. Разрешить одинаковые названия: они различаются идентификаторами. Пустой результат `trim()` не добавлять. Доступны добавление, переключение статуса и удаление; переименование не требуется исходным описанием. Пользовательский текст выводить через `textContent`.

Операция завершения в доменном слое создаёт независимый снимок успешного результата либо отсутствие результата для досрочного завершения и возвращает сброшенное состояние с пустыми задачами. UI сначала обновляет историю в памяти, затем пытается сохранить её. Ошибка записи не должна отменять завершение или оставлять повторно сохраняемую активную сессию. Альтернатива — очистить задачи до создания снимка — теряет историю.

### 4. Версионированная локальная история

Один ключ `focus-timer.history.v1` содержит объект с версией и массивом сессий. Запись: идентификатор, `startedAt`, `endedAt` как временные метки, локальная дата завершения `YYYY-MM-DD`, `targetMs`, `activeMs`, снимок задач. Адаптер проверяет структуру и значения прочитанных данных, перехватывает ошибки JSON и localStorage; при некорректной истории возвращает пустую историю и признак ошибки.

Дату завершения фиксировать по локальному календарю в момент завершения, без UTC-среза ISO. Статистика фильтрует этот ключ по текущей локальной дате и суммирует `activeMs` перед форматированием. Пересчитывать при завершении, загрузке, смене даты на очередном обновлении и `visibilitychange`. Порядок истории — новые записи сверху. Старые даты сохраняются, но не отображаются в разделе «Сегодня». Альтернатива — хранить только сегодняшние агрегаты — теряет задачи и детализацию.

Незавершённая сессия, её задачи и режим концентрации хранятся только в памяти. Это явное допущение: brief требует постоянного хранения только статистики. Ошибки хранения показывать спокойным встроенным сообщением, без модальных окон.

### 5. Интерфейс и полноэкранный режим

Использовать семантические кнопки, подписи полей и видимый фокус клавиатуры. Адаптивная компоновка переносит длинные названия и элементы управления; проверка минимальной ширины — 390 пикселей. Обновление секундомера не должно перехватывать фокус поля задачи.

Глубокая концентрация — независимый флаг представления, скрывающий второстепенные области без размонтирования состояния сессии. После включения предложить отдельную кнопку перехода в полный экран: так Fullscreen API вызывается из пользовательского жеста. Обработать отказ и отсутствие API. Escape выходит только из полноэкранного режима; кнопка выхода из концентрации снимает флаг и при необходимости вызывает выход из полного экрана. Альтернатива связывать сессию с fullscreen-состоянием приводит к нежелательным остановкам при Escape.

### 6. Проверки

Использовать `node:test` и `node:assert/strict` с искусственными временными метками, без реального ожидания 60 минут. Покрыть переходы, несколько пауз, задержки обновления, точную границу цели, превышение, сброс, форматирование, задачи, независимость снимков и суммирование. Адаптер хранилища тестировать внедряемым объектом с интерфейсом localStorage, включая повреждение и отказ записи. DOM, полноэкранный API, отсутствие внешних запросов и ширину 390 пикселей проверить вручную в браузере; автоматизацию браузера с внешними библиотеками не добавлять.

## Risks / Trade-offs

- Перевод системных часов влияет на разности временных меток → задокументировать ограничение и не использовать тики как источник времени.
- localStorage может быть недоступен или заполнен → сохранить результат в памяти и явно сообщить об ошибке сохранения.
- Перезагрузка теряет незавершённую сессию → указать границу хранения в README; успешно сохранённые записи восстанавливаются.
- Две вкладки могут перезаписать историю друг друга → первая версия рассчитана на одну активную вкладку; синхронизация вне объёма.
- Поддержка fullscreen различается → основной режим концентрации работает независимо от API.

## Migration Plan

Существующих данных и приложения нет: миграция не требуется. Добавить статические файлы, выполнить `node --test` и ручную проверку по README, затем использовать локальную статическую раздачу. Откат — вернуть предыдущую версию файлов; ключ истории не удалять автоматически. Изменение формата хранения в будущем потребует новой версии или явной миграции.
